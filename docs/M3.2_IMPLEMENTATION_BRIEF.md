# M3.2 — SEARCH UNIVERSE & QUALIFICATION IMPLEMENTATION BRIEF

**Status:** Ready for implementation
**Canonical parent:** `docs/MASTER.md`
**Scope:** M3.2 only. Do not implement M4+ intelligence engines.

## 1. Goal

Turn the confirmed M3.1 Service / Offer Map into a market-derived, owner-approved Search Universe.

Canonical flow:

CONFIRMED SERVICES/FACETS
→ SEED BUILDER
→ MARKET DISCOVERY
→ RAW QUERIES
→ FILTERING
→ NORMALIZATION
→ QUERY FAMILIES
→ SEARCH TOPICS
→ LIGHTWEIGHT PRELIMINARY QUALIFICATION
→ OWNER REVIEW
→ APPROVED SEARCH UNIVERSE

The system must reason above the keyword level. Raw queries remain auditable evidence.

Extend these; do not create parallel search-universe collections or pipelines.

## 3. Seed Builder — required

Search discovery must be seeded from **confirmed** `businessServices`, not from an arbitrary blank keyword box.

Build deterministic seed objects from:
- service
- project type
- audience
- market
- offering
- geography
- positioning
- need

Rules:
- Prefer owner-provided service names and owner-declared service-area geography.
- Website/AI facet values can enrich seeds but never replace owner truth.
- A single-project location discovered from a portfolio page is evidence, not automatically a target geography.
- Avoid combinatorial explosion. Use configurable seed caps and deterministic prioritization.
- Persist the seed provenance so every discovery result can be traced back to service/facet inputs.
- Do not call an LLM just to construct deterministic combinations.

## 4. Discovery

### GSC
Use current connected Search Console data for actual existing visibility.
Preserve query-level metrics and source provenance.

### Semrush
Use confirmed service/facet seeds for market discovery.
Reuse the existing governed Semrush adapter.
Every provider call must pass the universal governor.
Never bypass cache/quota/budget/circuit breaker.

### Provider boundaries
Do not implement SERP or AI discovery providers in M3.2 unless already present and required for a tested acceptance path. Keep adapters replaceable for later milestones.

## 5. Filtering

Keep filtering conservative.

Automatically exclude only when supported by an explicit owner-authored exclusion rule.

Do not silently discard ambiguous or low-volume topics.

Preserve raw evidence and the reason for any exclusion.

## 6. Normalization and Query Families

Keep raw queries intact in `keywords`.

Improve deterministic grouping so that:
- duplicate phrases across sources map to one query record/topic;
- query families can contain lexical variants;
- grouping remains explainable;
- Hebrew morphology/prefix limitations are explicitly handled as a known limitation unless a reliable deterministic solution is proven;
- normalization must not destroy the original query text or provenance.

Do not use AI for basic deduplication.

## 7. Search Topic model

A Search Topic is a document above its raw queries.

Where useful, extend the existing topic shape additively with:
- `seedRefs`
- `sourceCount`
- `sources`
- `qualification`
- `qualificationReasons`
- `preliminaryIntent` (lightweight only; NOT the future full Intent object)
- `lastDiscoveredAt`

Do not make topic creation equal page creation.

## 8. Lightweight preliminary qualification

M3.2 may attach a lightweight preliminary intent/category and qualification evidence to topics, but must NOT implement:
- full Intent object
- canonical page ownership
- cannibalization engine
- CREATE vs IMPROVE
- Decision Engine
- Opportunity Engine
- Time-to-Impact
- Learning model

Owner decisions remain first-class:
- relevant
- priority
- brand_strategic
- unsure
- exclude

Strategic/brand topics remain valid even with low or missing measurable volume.

## 9. Rejection / negative signal

Rejected services and topics are durable negative signals.

Do not re-propose exact or close variants casually.

Preserve enough identity/provenance to explain why something was excluded.

Do not use destructive deletion as the mechanism for rejection.

## 10. Cost and safety

M3.2 inherits the universal external-provider rule from `docs/MASTER.md`.

Required:
- deterministic cache identity
- cache before provider call
- fail closed
- explicit paid refresh
- per-operation/biz/global budgets
- usage ledger with decision/reason
- no paid calls on render/page-load
- no automatic retry loops that can spend money

Important current cross-cutting note:
Google API ingestion in `functions/visibility.js` still needs to be brought under the universal governor before Production Ready, but this does not block M3.2 as long as M3.2 does not add new ungoverned paid/quota-limited calls.

## 11. UI

Keep the existing Service Map/Search Topics UI style.

The user should be able to:
- see which confirmed service/facets generated seeds;
- understand where a topic came from;
- review raw queries and their sources;
- see conservative qualification/reasons;
- approve/reject/prioritize/mark brand-strategic/unsure;
- manually add a topic;
- see excluded/rejected items as historical negative signals.

Do not redesign unrelated workspace tabs.

## 12. Acceptance tests

M3.2 is complete only when the real Hagar case proves:

1. confirmed Service Map produces deterministic seeds;
2. owner geography is preferred over portfolio/project-location geography;
3. at least two configured discovery sources contribute evidence (GSC + Semrush when Semrush is available);
4. identical discovery requests reuse cached provider results;
5. a changed seed creates a new governed request;
6. provider failures/lookup failures fail closed;
7. every raw query keeps source provenance;
8. repeated discovery does not create duplicate query records;
9. lexical variants can be grouped without losing raw queries;
10. explicit owner exclusions remove candidates with an auditable reason;
11. ambiguous candidates are not silently deleted;
12. Search Topics sit above raw queries;
13. owner status changes persist;
14. rejected topics remain rejected across subsequent discovery;
15. approved Search Universe is a clean input for M4;
16. discovery does not create pages/tasks/opportunities as a side effect;
17. no provider call occurs on page render/load;
18. all relevant automated tests pass;
19. browser acceptance passes on the real app;
20. no M4+ functionality was smuggled into M3.2.
